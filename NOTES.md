# Технические заметки

Допущения по предметной области (как считать деньги) - в [DECISIONS.md](DECISIONS.md). Здесь - решения по устройству программы, ограничения и план.

## Принятые технические решения

**Только стандартная библиотека.** Задачу «прочитать три CSV и посчитать» не оправдывают pandas или pydantic; программу можно запустить на любой машине с Python без установки. Тесты - `unittest`, чтобы тоже не требовать зависимостей (`pytest` их подхватывает).

**`Decimal` везде, `float` нигде.** Сумма разбирается регулярным выражением, а не `Decimal(text)`: тот молча принимает `1e3`, `NaN`, `+5`. Больше двух знаков после точки - ошибка, а не округление. В JSON суммы - строки, потому что большинство JSON-парсеров читают числа как `float`.

**Ядро без ввода-вывода.** `calculator.py` получает готовый `Dataset` и дату и возвращает `Report`. «Сегодня» читает только CLI. Благодаря этому расчёт полностью детерминирован и тестируется без файлов.

**Откат на дату вместо снимка.** Вместо хранения снимков по датам расчёт строится из дат событий (`completed_at`, `cancelled_at`, `paid_at`, `refunded_at`, `created_at`). Один и тот же код даёт отчёт на любой день, в том числе исторический.

**Предупреждение «из будущего».** Расчёт дополнительно запускается на `date.max`, чтобы заметить переплату, которая возникнет из-за платежей и событий после даты отчёта (в данных так бывает: P-8 от 12.11 при отчёте на 10.11). Побочный эффект - предупреждения этого расчёта отбрасываются, иначе они дублировались бы.

**Инвариант сохранения денег как `assert`.** Проверка «сумма по работам + нераспределённое = выплачено» стоит прямо в расчёте. Если когда-нибудь правка распределения потеряет копейку, программа упадёт, а не выдаст тихо неверный отчёт. Для расчётов с деньгами это осознанный выбор в пользу громкой ошибки.

**Все ошибки данных - разом.** Загрузчик собирает ошибки списком, а не падает на первой: выгрузку чинят за один проход. Исключение - отсутствие файла или обязательной колонки: без них продолжать нечего.

**Три формата вывода при одном расчёте.** Расчёт не знает о представлении, поэтому добавление формата не затрагивает логику (см. ARCHITECTURE.md).

**Дата по умолчанию - сегодня.** Удобно для ежедневной работы, но повторный запуск завтра даст другой результат; для воспроизводимых отчётов дату нужно указывать явно (в записке бухгалтеру и README так и сделано).

## Известные ограничения

- **Частичных возвратов нет.** `refunded` - возврат платежа целиком; поля «сумма возврата» в выгрузке нет.
- **Нет валют, НДС, удержаний и штрафов.** Все суммы - рубли, цена работы - единственное, что причитается за неё.
- **Нет истории изменений цены, суммы договора и привязки платежей.** Используются значения из выгрузки. Если цену работы или привязку платежа правили задним числом, отчёт на прошлую дату этого не увидит.
- **Нет даты создания работы.** Работа, заведённая позже даты отчёта, всё равно попадёт в отчёт как «запланирована»; платёж с `created_at` позже даты отчёта в расчёт не попадает.
- **Распределение платежей по работам - эвристика** (FIFO по приёмке). Явная привязка платежа всегда приоритетнее; расчётная часть отдельно видна в отчёте, но истинной привязки по неразмеченным платежам мы знать не можем.
- **Платёж, привязанный к работе, не может покрыть другие работы напрямую**: излишек сверх цены работы уходит в общий пул и гасит принятые работы по FIFO (см. `work_overpaid`).
- **Файл читается целиком в память.** Для сотен тысяч строк это не проблема; для миллионов потребовалась бы потоковая обработка.
- **Фильтр по подрядчику, периоду и т.п. нет** - только по договору (`-c`).
