# Архитектура

## Обзор

Программа - конвейер из четырёх шагов, где вся бизнес-логика собрана в одном модуле без ввода-вывода:

```
 data/*.csv ──► loader ──► Dataset ──► calculator ──► Report ──► render ──► table / JSON / CSV
                  ▲                        ▲                                      ▲
                  │                        │                                      │
               money, models ──────────────┴──────────────────────────────────────┘
                                   cli: аргументы, дата «сегодня», файлы, коды возврата
```

Технологии: Python 3.9+, только стандартная библиотека (`csv`, `decimal`, `dataclasses`, `argparse`, `json`). Тесты - `unittest` (запускаются и через `pytest`).

## Компоненты

| Модуль | Ответственность | Чего здесь нет |
|---|---|---|
| `money.py` | строгий разбор суммы в `Decimal`, форматирование (`300 000,00` для людей, `300000.00` для машин) | расчётов |
| `models.py` | неизменяемые dataclass'ы `Contract`, `Work`, `Payment`, `Dataset` и перечисления статусов | логики |
| `loader.py` | чтение CSV (UTF-8, с BOM или без), валидация полей, статусов и согласованности дат, проверка ссылок между файлами | расчётов, «предупреждений» |
| `calculator.py` | **вся бизнес-логика**: откат на дату, распределение платежей, итоги, предупреждения. Чистые функции | чтения файлов, форматов вывода, «сегодняшней» даты |
| `render.py` | преобразование `Report` в текст таблицы, JSON или CSV | расчётов |
| `cli.py` | разбор аргументов, чтение данных, вызов расчёта и рендера, коды возврата | бизнес-правил |

Зависимости направлены строго вниз: `cli → {loader, calculator, render} → models, money`. `calculator` не знает ни про файлы, ни про формат вывода; `render` не знает, как считаются суммы.

## Поток данных

1. **cli** разбирает `--date` (если нет - `date.today()`; это единственное место, где программа читает часы) и вызывает `load_dataset(data_dir)`.
2. **loader** читает три CSV, превращает строки в модели. Ошибки строк копятся в список; затем проверяются ссылки (работа → договор, платёж → договор и работа, работа платежа принадлежит тому же договору). При любой ошибке выбрасывается `DataError` со всем списком.
3. **calculator.calculate(dataset, as_of)** для каждого договора, подписанного не позже даты отчёта:
   1. определяет состояние каждой работы на дату (`planned` / `done` / `cancelled`) и «живую» сумму каждого платежа (`paid_net`);
   2. делит деньги на привязанные к работам и общий пул платежей без привязки;
   3. привязанные платежи кладёт в свои работы (не больше цены; излишек уходит в пул);
   4. пул раскладывает по принятым работам в порядке приёмки (FIFO); остаток пула - «аванс, не закреплённый за работами»;
   5. считает итоги договора и собирает предупреждения.
4. **render** превращает `Report` в строку нужного формата, **cli** выводит её на экран или в файл.

## Ключевые модели результата

- `WorkLine` - строка по работе: цена, выплачено, из них по явной привязке, осталось, состояние на дату.
- `ContractReport` - итоги договора: к оплате с учётом отмен, выплачено, осталось, переплата, «принято, но не оплачено», нераспределённый аванс, очередь.
- `Report` - дата, список `ContractReport`, предупреждения, пропущенные договоры.

## Инварианты

Расчёт проверяет себя на каждом договоре (`assert` в `_calculate_contract`):

> сумма «выплачено» по работам + нераспределённый аванс = выплачено по договору

То есть деньги не появляются и не теряются, как бы ни были разложены платежи. Дополнительно тесты проверяют инвариант на «грязных» данных (платёж по отменённой работе, переплата по работе).

## Расширение

- **Новый формат вывода** - функция `Report -> str` в `render.py` и запись в словаре `_RENDERERS` в `cli.py`. Расчёт не меняется.
- **Другое правило распределения платежей** - заменить шаг 4 в `calculator._calculate_contract` (единственное место, где определяется, «за что рассчитались»). Итоги договора от этого не зависят.
- **Другой источник данных** (БД, API) - любой код, возвращающий `Dataset`; `calculator` и `render` не изменятся.
